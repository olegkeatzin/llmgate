# LLMGate

Корпоративный шлюз к языковым моделям: **SGLang** для инференса, **LiteLLM Proxy** для ключей,
лимитов и аналитики, тонкий **портал** для входа сотрудников через LDAP и выдачи ключа на сутки.

Развёртывание — Docker Compose на сервере с двумя NVIDIA A100. Модели, лимиты и резервные
каналы описываются файлами в Git, а не кликами в интерфейсе.

---

## Что умеет

- **Модели на SGLang** — по контейнеру на модель, конфиг в `models/<имя>/model.yaml`.
  Новая модель = новый YAML + `make models`. Резервные каналы — тоже в YAML.
- **Ключи и лимиты** — виртуальные ключи LiteLLM: `rpm`/`tpm`, параллельные запросы,
  бюджеты, срок жизни, привязка к моделям. Хранятся в PostgreSQL.
- **Вход через LDAP** — сотрудник вводит доменный логин и пароль, получает ключ
  (по умолчанию на 24 часа) прямо в браузере. Пароль нигде не сохраняется.
- **Роли из LDAP-групп** — `config/access.yaml`: группа → модели + лимиты + срок ключа.
  Есть ручные исключения для отдельных логинов.
- **Резервные каналы** — другая модель на этом же сервере или эндпоинт на другом сервере;
  настраивается в `config/router.yaml`, проверяется вручную за две минуты.
- **Аналитика** — LiteLLM пишет журнал расходов в PostgreSQL и показывает его в UI:
  кто, сколько, по какой модели. Промпты в журнал не попадают.

## Как это устроено

```
                    ┌──────────────────────────────┐
   сотрудник ──────▶│  portal :8080                │
   (браузер)        │  LDAP-вход → выпуск ключа    │──── LDAP ───▶ AD / OpenLDAP
                    └──────────────┬───────────────┘
                                   │ management API (мастер-ключ)
                                   ▼
   приложение ─────▶┌──────────────────────────────┐
   (OpenAI SDK)     │  litellm :4000               │──── PostgreSQL
     sk-…           │  ключи, лимиты, роутинг,     │     (ключи, бюджеты, расходы)
                    │  резервные каналы, аналитика │
                    └───────┬──────────────┬───────┘
                            │              │
                    ┌───────▼──────┐  ┌────▼─────────────┐
                    │ SGLang       │  │ резервный канал  │
                    │ qwen3-32b    │  │ другой сервер /  │
                    │ GPU 0–1      │  │ внешний API      │
                    └──────────────┘  └──────────────────┘
```

| Компонент | За что отвечает | Где настраивается |
|---|---|---|
| **SGLang** | загрузка весов, инференс, GPU | `models/*/model.yaml` |
| **LiteLLM Proxy** | ключи, лимиты, роутинг, резервы, аналитика, UI | `config/litellm.settings.yaml` + генератор |
| **Portal** | LDAP-вход, выпуск и отзыв ключа сотрудника | `config/access.yaml` + `.env` |
| **PostgreSQL** | состояние LiteLLM: ключи, бюджеты, журнал расходов | `.env` |

Портал намеренно маленький: он не дублирует админку LiteLLM, а только превращает
LDAP-вход в ключ. Почему так — в [ADR 0001](docs/adr/0001-thin-portal.md).

## Быстрый старт

Полный гайд от чистого сервера (драйвер → .env → LDAP → модель → ключ):
**[docs/00-setup.md](docs/00-setup.md)**. Ниже — сокращённая версия для сервера,
где Docker и nvidia-container-toolkit уже стоят.

```bash
git clone <репозиторий> llmgate && cd llmgate

make env                      # создаёт .env со случайными секретами

$EDITOR .env                  # заполните LDAP_* и PUBLIC_API_BASE_URL

# Реестр моделей пуст — выберите свою. Пример под 2×A100:
make example NAME=qwen3-32b

make up                       # соберёт портал, поднимет БД, LiteLLM и модель

make ps                       # ждём healthy у контейнера sglang-<ваша-модель>
```

Первый запуск SGLang качает веса вашей модели в `data/hf-cache` и грузит их
на GPU — это 5–20 минут в зависимости от размера и канала. Прогресс:

```bash
make logs-model MODEL=qwen3-32b
```

Когда всё поднялось:

| Что | Адрес |
|---|---|
| Портал сотрудника | `http://<host>:8080` |
| API (OpenAI-совместимый) | `http://<host>:4000/v1` |
| Админ-UI LiteLLM | `http://<host>:4000/ui` (логин/пароль из `.env`) |

Проверка API мастер-ключом (до выдачи первого пользовательского ключа):

```bash
curl http://localhost:4000/v1/chat/completions \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "qwen3-32b", "messages": [{"role": "user", "content": "Привет"}]}'
```

## Как сотрудник получает ключ

1. Открывает `http://<host>:8080` и вводит доменный логин/пароль.
2. Портал проверяет пароль в LDAP, находит группы и роль в `config/access.yaml`.
3. Создаёт в LiteLLM виртуальный ключ: модели роли, `rpm`/`tpm`, `max_parallel_requests`,
   `duration=24h`, `user_id=логин`.
4. Показывает ключ **один раз** — дальше его знает только сотрудник.
5. В том же кабинете видны все его ключи (из LiteLLM), срок и расход; можно отозвать
   и выпустить новый.

Ключ живёт 24 часа. Продление — выпуск нового ключа, старый отзывается кнопкой
(или истекает сам). Это осознанное требование: сутки — компромисс между удобством
и ущербом от утечки.

## Добавить модель

```bash
python3 tools/llmgate.py add qwen2.5-72b --hf-repo Qwen/Qwen2.5-72B-Instruct --tp 2 --gpus 0,1
$EDITOR models/qwen2.5-72b/model.yaml     # контекст, память, резервы, включение
make models                                # compose + конфиг LiteLLM + каталог
make up                                    # поднять
```

Или взять готовый пример: `make example NAME=qwen3-32b` (список — `ls examples/models`).
Примеры **не загружаются**, пока вы их не скопируете в `models/`.

Полное описание полей, раскладок на 2×A100 и офлайн-загрузки весов —
[docs/02-models.md](docs/02-models.md).

## Роли и лимиты

Одна роль = один блок в `config/access.yaml`:

```yaml
policies:
  - id: users
    ldap_groups: ["LLM-Users"]
    models: ["*"]              # или явный список: ["qwen3-32b"]
    key_ttl_hours: 24
    max_active_keys: 2
    rpm_limit: 60
    tpm_limit: 100000
    max_parallel_requests: 8
```

Применение: `make restart-portal`. Правки ролей версионируются и проходят ревью.
Подробно — [docs/04-access.md](docs/04-access.md).

## Резервные каналы

В `config/router.yaml` — это блок `router_settings` LiteLLM в его родном формате:

```yaml
fallbacks:
  - qwen3-32b: [qwen3-8b, llm2-qwen3-32b]
```

LiteLLM сначала повторит запрос (`num_retries: 2`), потом пойдёт по цепочке.
`qwen3-8b` — локальная вторая модель, `llm2-qwen3-32b` — пример внешнего эндпоинта
(`kind: RemoteModel`, без контейнера). Выключенные цели исключаются из конфига
с предупреждением при генерации.

Проверка: поднять резерв, остановить основную модель (`docker compose stop sglang-qwen3-32b`)
и повторить запрос — ответ должен прийти от резерва. Детали —
[docs/02-models.md](docs/02-models.md#резервные-каналы).

```
  litellm.generated.yaml # СГЕНЕРИРОВАН (в git не хранится)

tools/
  llmgate.py             # реестр → compose + конфиг LiteLLM
  gen_secrets.py         # .env со случайными секретами
tests/                   # pytest: реестр, роли, портал (без сети)
docs/                    # документация
```

## Требования

- Linux, Docker Engine 24+, Docker Compose v2.
- NVIDIA Driver 550+, nvidia-container-toolkit.
- 2×A100 (рекомендуется 80 ГБ) — базовая раскладка рассчитана на 65 ГБ весов + KV-кэш.
- 150 ГБ диска: веса (~65 ГБ), кэш, PostgreSQL, логи.
- Python 3.11+ на хосте — только для `tools/llmgate.py` и тестов (нужен `PyYAML`).

## Ограничения, о которых стоит знать

- Портал не хранит значения ключей: ключ показывается один раз. Потеряли — отзовите и выпустите новый.
- Сессия портала — зашифрованная cookie; серверного хранилища сессий нет. Отозвать все сессии
  разом можно сменой `PORTAL_SESSION_KEY`.
- Админка LiteLLM (/ui) использует отдельный пароль и не ходит в LDAP. Так задумано:
  администраторов единицы, а вход по LDAP для них — лишняя поверхность атаки.
  Если нужен единый вход, это Enterprise-функция LiteLLM (SSO через Keycloak/AAD).
- Портал запускается одним процессом: счётчик неудачных входов хранится в памяти.
  При горизонтальном масштабировании понадобится общее хранилище.
