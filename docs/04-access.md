# Доступ: роли, лимиты, ключи

Все правила доступа — в одном файле `config/access.yaml`. Он лежит в Git, проходит
ревью и откатывается как любой код.

## Структура

```yaml
schema: 1

defaults:
  key_ttl_hours: 24      # значение по умолчанию для ролей без своего срока

policies:
  - id: engineer          # слаг, не меняется после появления в git-истории
    name: Разработчик     # как называется в интерфейсе
    ldap_groups: ["LLM-Engineers"]
    models: ["qwen3-32b", "qwen3-8b", "bge-m3"]
    key_ttl_hours: 24
    max_active_keys: 2
    rpm_limit: 120
    tpm_limit: 200000
    max_parallel_requests: 8

overrides:                 # логин → id роли, перекрывает группы
  ivanov: admin
```

## Как выбирается роль

1. Если логин есть в `overrides` — берётся указанная роль, группы игнорируются.
2. Иначе просматриваются `policies` **сверху вниз**; срабатывает первая, где есть
   пересечение с группами сотрудника (или `"*"`).
3. Если ничего не подошло — вход запрещён, ключ не выдаётся.

Порядок в файле = приоритет. Поэтому узкие роли ставьте выше широких: администратор
выше разработчика, разработчик выше «всех остальных».

Группы сравниваются без учёта регистра, и по полному DN, и по CN — можно писать
`LLM-Engineers`, `cn=llm-engineers,ou=groups,dc=corp,dc=local` или `llm-engineers`.

## Что роль даёт LiteLLM

| Поле `access.yaml` | Параметр `/key/generate` | Действие |
|---|---|---|
| `models` | `models` | какие модели доступны ключу |
| `key_ttl_hours` | `duration` | срок жизни ключа (`"24h"`) |
| `rpm_limit` | `rpm_limit` | запросов в минуту |
| `tpm_limit` | `tpm_limit` | токенов в минуту |
| `max_parallel_requests` | `max_parallel_requests` | одновременных запросов |
| `budget_usd` + `budget_duration` | `max_budget`, `budget_duration` | денежный лимит |

`max_active_keys` проверяет сам портал: считает действующие ключи через `/key/list`
и не даёт выпустить лишний. `"*"` в `models` разворачивается в список включённых
моделей на момент выпуска — выключенные модели в ключ не попадают.

Цены задаются в `models/<имя>/model.yaml` (`pricing`). Пока они нулевые, `budget_usd`
не срабатывает, а статистика показывает токены и запросы. Для внутреннего
«биллинга» поставьте условные цены — тогда `max_budget` начнёт ограничивать.

## Срок ключа и ротация

По умолчанию — сутки (требование эксплуатации). Это значит:

- сотрудник раз в день выпускает новый ключ, старый отзывается кнопкой или истекает;
- потерянный ключ не восстановить — у LiteLLM хранится только хеш;
  поэтому «показать ещё раз» в портале отсутствует принципиально;
- `max_active_keys` не даёт накопить десяток живых ключей: старые придётся отозвать.

Ротация в приложении: положите ключ в переменную окружения/секрет-хранилище
и обновляйте раз в сутки. Если это неудобно для сервисных интеграций, заведите
отдельную роль с более длинным `key_ttl_hours` и выдавайте её только сервисным
учёткам через `overrides`.

## Примеры ролей

### Базовый доступ всем сотрудникам

```yaml
- id: all-staff
  name: Сотрудник
  ldap_groups: ["*"]          # любой, кто успешно вошёл в LDAP
  models: ["qwen3-32b"]
  key_ttl_hours: 24
  max_active_keys: 1
  rpm_limit: 20
  tpm_limit: 20000
```

Внимание: `"*"` пускает **всех**, у кого есть доменная учётка. Если нужен только
отдел — перечислите группы явно.

### Подрядчик на неделю

```yaml
- id: contractor
  name: Подрядчик
  ldap_groups: ["LLM-Contractors"]
  models: ["qwen3-8b"]
  key_ttl_hours: 72
  max_active_keys: 1
  rpm_limit: 10
  tpm_limit: 10000
```

### Сервисная учётка

```yaml
- id: automation
  name: Автоматизация
  ldap_groups: ["LLM-Automation"]
  models: ["qwen3-32b"]
  key_ttl_hours: 168
  max_active_keys: 1
  rpm_limit: 300
```

### Персональное исключение

```yaml
overrides:
  ivanov: admin          # тестировщик смотрит все модели
  petrov: contractor
```

## Применение изменений

```bash
$EDITOR config/access.yaml
make restart-portal
```

Что происходит с уже выданными ключами: **ничего**. Ключ содержит права на момент
выпуска; новые лимиты применятся к следующему ключу. Если нужно немедленно сузить
доступ — отзовите ключи пользователя в UI LiteLLM или в его кабинете.

Сессия портала живёт 8 часов и содержит группы на момент входа. Сотрудник, которого
перевели в другую группу, увидит новую роль после повторного входа.

## Кто что видит

- **Сотрудник** — только свои ключи (портал фильтрует `/key/list` по `user_id`).
- **Администратор** — все ключи, расходы, журналы в UI LiteLLM:
  `http://<host>:4000/ui` → Virtual Keys / Usage.
- **Аудит входов** — логи контейнера `portal`: `event=login.ok`, `login.failed`,
  `login.denied`, `key.created`, `key.revoked`. Соберите их в свой SIEM через
  `docker logs` / journald.

## Частые вопросы

**Почему роль не применяется?** Портал кэширует политики при старте — нужен
`make restart-portal`. И проверьте, что группа в `ldap_groups` совпадает с тем,
что реально пришло из LDAP (`python -m app.ldapcheck`).

**Можно ли выдать доступ к одной модели без ключа?** Нет. Доступ = ключ.

**Можно ли ограничить по IP?** Лимиты LiteLLM этого не умеют; ставьте ограничения
на reverse proxy или файрволе.

**Что будет, если удалить роль, которая кому-то назначена?** В `access.yaml` нет
ссылочной целостности: сотрудник просто перестанет получать ключ (вход покажет
«нет доступа»). Уже выданные ключи доживут до истечения срока.
