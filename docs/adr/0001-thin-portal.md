# ADR 0001. Портал — тонкая прослойка над LiteLLM

**Статус:** принято
**Дата:** 2026-11-19

## Контекст

Требования к стенду: SGLang для моделей, LiteLLM + PostgreSQL для ключей и лимитов,
вход сотрудников через LDAP с выдачей ключа на сутки, резервные каналы.

LiteLLM Proxy из коробки закрывает почти всё:

| Требование | Штатное средство LiteLLM |
|---|---|
| выпуск ключей с TTL | `POST /key/generate`, `duration` |
| лимиты | `rpm_limit`, `tpm_limit`, `max_parallel_requests`, `max_budget` |
| доступ к моделям | `models` в ключе/команде |
| роли и группы | команды (teams), роли участников |
| мониторинг и аналитика | журнал расходов, UI `/ui`, эндпоинты статистики |
| резервные каналы | `router_settings.fallbacks` |
| администрирование | веб-UI `/ui` |

Не закрыто ровно одно: **LDAP**. В LiteLLM нет LDAP-провайдера; SSO (OIDC/SAML) —
функция Enterprise-лицензии, и она всё равно не даёт «вход по доменному паролю»
без промежуточного IdP.

## Решение

Портал делает только две вещи: проверяет пароль в LDAP и выпускает ключ через
management API LiteLLM. Всё остальное остаётся в LiteLLM.

Следствия, зафиксированные осознанно:

1. **Нет второй админки.** Роли и доступ — `config/access.yaml` в Git. Лимиты,
   ключи, расходы, команды — UI LiteLLM. Никакого CRUD ролей в портале.
2. **Нет второй БД.** Ключи читаются из LiteLLM (`/key/list?user_id=`), сессия — в
   зашифрованной cookie. Портал не хранит состояния.
3. **Ключ показывается один раз.** LiteLLM не отдаёт значение ключа повторно,
   и портал не создаёт для этого хранилище.
4. **Портал ≈ 700 строк.** Всё, что больше, — дублирование LiteLLM.

## Рассмотренные альтернативы

**A. Полноценная самописная админка** (роли, пользователи, аналитика в портале).
Отклонено: второй источник истины, миграции, расхождение с LiteLLM, втрое больше кода
и поверхностей для ошибок. Именно так выглядела первая версия — и это было лишним.

**B. Keycloak + SSO LiteLLM Enterprise.** Плюс: почти ноль своего кода.
Минус: платная лицензия, ещё один stateful-сервис (Keycloak) со своей БД, отдельная
настройка федерации LDAP. Для двух A100 и нескольких десятков сотрудников
неоправданно; при появлении требования «единый вход во все сервисы» — правильный путь.

**C. Только UI LiteLLM, без портала.** Невозможно: сотрудники не смогут войти
по LDAP, а заводить им отдельные логин/пароль в LiteLLM — худший вариант.

## Последствия

Плюсы: мало кода, один источник истины для ключей, обновление LiteLLM не ломает
админку, права ревьюятся в Git, нет второй БД для бэкапа.

Минусы и как жить:

- Ключ не восстановить. Лечится выпуском нового; `max_active_keys` ограничивает бардак.
- Роли меняются перезапуском портала (`make restart-portal`), а не кликом.
  Это минус для «админки», плюс для аудита.
- Админ входит в UI LiteLLM отдельным паролем. Приемлемо: администраторов единицы.
- Нет серверного отзыва сессий. Смена `PORTAL_SESSION_KEY` разлогинивает всех.

## Когда пересматривать

- Появилось требование единого входа во все корпоративные сервисы → вариант B.
- Понадобились per-user исключения в UI и самообслуживание команд → переносить
  управление в LiteLLM teams, а не отращивать портал.
- Больше ~200 сотрудников и несколько реплик портала → общее хранилище сессий.
